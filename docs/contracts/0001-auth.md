# Resumen

Para entender el flujo de autenticación y autorización, leer el [ADR técnico 0003](../adr/tecnico/0003-autenticacion-con-cookie.md)

| Endpoint | Requiere sesión | Qué hace | Éxito | Errores |
|---|---|---|---|---|
| `POST /auth/login` | No | Verifica usuario y contraseña, crea la cookie de sesión y devuelve el usuario | 200 | 400, 401 |
| `GET /auth/me` | Sí | Devuelve el usuario de la sesión actual | 200 | 401 |
| `POST /auth/logout` | No | Cierra la sesión y borra su cookie | 204 | — |

Los demás endpoints protegidos responden 401 sin sesión y 403 si ninguno de los roles del usuario alcanza el rol mínimo del endpoint (ver el [ADR 0011](../adr/negocio/0011-acceso-por-rol-minimo.md)).

# Endpoints

## POST `/auth/login`

Permite al usuario iniciar sesión.

### Request

El frontend envía:

```json
{
  "username": "string",
  "password": "string"
}
```

### Response

El backend responde con los datos del usuario.

```json
{
  "id": number,
  "nombreUsuario": "string",
  "nombre": "string",
  "apellido": "string",
  "roles": string[],
  "permisos": string[]
}
```

Se puede ampliar según necesidad.

### Reglas de validación

Para el usuario actualmente se encuentran preestablecidas las siguientes reglas:

| Campo | Tipo | Reglas |
|---|---|---|
| `username` | `string` | Obligatorio, 4 a 50 caracteres. Se recorta antes de validarlo, para que un valor como `"ab    "` no sea válido |
| `password` | `string` | Obligatorio |

### Códigos HTTP

- **200 Ok**: credenciales válidas y usuario activo.
- **400 Bad Request**: falta un campo o no cumple el formato correcto la request. El backend devuelve su respuesta de error estándar.
- **401 Unauthorized**: credenciales inválidas o usuario inactivo (informar desde el backend).

## POST `/auth/logout`

Cierra la sesión. No requiere sesión: se puede llamar siempre.

### Códigos HTTP

- **204**: la sesión se cierra, así que una copia de la cookie deja de valer, y la cookie se borra (`Set-Cookie: chiga_auth=; expires=<fecha pasada>`). Sin body.

## GET /auth/me

Devuelve el usuario de la sesión actual. El frontend lo llama al cargar la app.

### Response

El backend responde con los datos del usuario.

```json
{
  "id": number,
  "nombreUsuario": "string",
  "nombre": "string",
  "apellido": "string",
  "roles": string[],
  "permisos": string[]
}
```

Se puede ampliar según necesidad.

### Respuestas

- **200**: hay una sesión válida. Body: `UsuarioDTO`. Renueva la expiración deslizante de la cookie cuando ya pasó la mitad de su duración ([ADR técnico 0005](../adr/tecnico/0005-baja-de-usuario-sin-corte-inmediato-de-sesion.md)).
- **401**: no hay cookie, venció, fue alterada, su sesión se cerró o el usuario fue dado de baja. Body: ProblemDetails. Si fue dado de baja, además cierra la sesión y borra la cookie.

Cualquier código de error devuelve una respuesta mediante ProblemDetails nativo de C#.

## Todos los demás endpoints

Cualquier endpoint protegido responde, con body ProblemDetails y sin redirigir:

- **401** si no hay una sesión válida. El frontend redirige al login.
- **403** si hay sesión pero ninguno de los roles del usuario alcanza el rol mínimo del endpoint. El frontend muestra un aviso y no cierra la sesión.

Estos endpoints no revisan si el usuario sigue activo: una cookie vigente sigue siendo válida aunque el usuario haya sido dado de baja. Ver el [ADR técnico 0005](../adr/tecnico/0005-baja-de-usuario-sin-corte-inmediato-de-sesion.md).
